# Gate CI and keep a reviewed baseline

<p class="inv-eyebrow">WALKTHROUGH 06 · CI &amp; BASELINES</p>

Make a scan fail when findings need attention, then carry a specific acceptance decision into the next run. You will see the difference between changing the gate and accepting existing findings.

<div class="inv-journey-meta" markdown="1">

**You need:** The [installed CLI](../INSTALLATION.md) and shipped `examples/vulnerable` fixture. No AI account is needed. Run from the prepared workspace root containing `examples/`, with `invscan` on PATH.

**You will create:** A baseline file and a report that keeps accepted findings visible as suppressed.

</div>

## 1. Watch the finding gate fail

<div class="inv-step" markdown="1">

Run the vulnerable example in quiet mode, as a CI job might. This mode keeps diagnostics and the exit status while suppressing the human report.

<!-- invscan-step:06:quiet_gate -->
```sh
invscan examples/vulnerable --quiet  # Expected exit 1
```

<div class="inv-result" markdown="1">

**You should see** no normal report in the terminal, and **exit 1**. The fixture has findings at or above the default high-severity threshold. This is the expected result, not an installation error.

Check the exit status immediately: use `$?` in Bash/Zsh or `$LASTEXITCODE` in PowerShell.

</div>

</div>

## 2. See what changing the gate actually does

<div class="inv-step" markdown="1">

Run the same scan with the finding threshold disabled and request a JSON summary.

<!-- invscan-step:06:disabled_gate -->
```sh
invscan examples/vulnerable --fail-on none --summary-json
```

<div class="inv-result" markdown="1">

**You should see** **11 open findings** and **exit 0**. The findings remain open; `--fail-on none` only changes whether findings trigger the exit gate. Errors and incomplete work still return exit 2.

</div>

For a real pipeline, choose the lowest severity that should block the job: `critical`, `high`, `medium`, `low`, `info` or `none`. Use either `--quiet` or `--summary-json`; they cannot be combined.

</div>

## 3. Write a baseline candidate

<div class="inv-step" markdown="1">

Create a candidate that names the existing fixture findings and records why this demonstration accepts them. The supplied reason is explicitly for this inert test fixture.

<!-- invscan-step:06:write_baseline -->
```sh
invscan examples/vulnerable --write-baseline scan-report/scenarios/06-baseline.json --baseline-reason 'TEST ONLY: accepted inert documentation fixture; not production approval.' --summary-json  # Expected exit 1
```

<div class="inv-result" markdown="1">

**You should see** a new `scan-report/scenarios/06-baseline.json` file, **11 open findings** and **exit 1**. Writing a baseline does not apply it to the current run.

</div>

Open the JSON file in your editor. Inspect the stable finding IDs and the acceptance reason. In your own project, review each candidate and record the actual evidence, owner and acceptance record before applying it. Do not reuse the fixture reason as production approval.

</div>

## 4. Apply the reviewed baseline

<div class="inv-step" markdown="1">

Apply that candidate to a fresh scan of the same fixture and save a report.

<!-- invscan-step:06:apply_baseline -->
```sh
invscan examples/vulnerable --baseline scan-report/scenarios/06-baseline.json --report scan-report/scenarios/06-baselined --summary-json
```

<div class="inv-result" markdown="1">

**You should see** **0 open findings**, **11 suppressed findings** and **exit 0**. Open `scan-report/scenarios/06-baselined/report.html` to inspect the retained findings and acceptance evidence.

</div>

A baseline matches the recorded finding IDs. It does not grant a blanket exception for new findings and does not establish that a vulnerability was fixed.

</div>

## Use the result in your pipeline

| Exit | What the job should report |
|---|---|
| **0** | The selected work completed below the configured open-finding threshold. |
| **1** | Open findings reached the configured threshold. |
| **2** | The scan or requested review was incomplete or failed. Investigate the diagnostic before trusting the result. |

Keep the reviewed baseline under your own change-control process and save the generated report as a CI artifact. For the complete file format, see [finding baselines](../CLI.md#finding-baselines).
